## 4. Changes from the P2 spec and the P3 plan

Every change below made the kit stricter or the measurement more trustworthy. None was made to save effort.

| # | Change | Why |
| --- | --- | --- |
| 1 | **H02 also blocks `Read` of secret files** (`.env*`, keys, credentials) | Project deny rules apply only after the project settings load and the folder is trusted. Plugin evals load no project settings at all. The hook works everywhere pilot is active |
| 2 | **H02 protects `.pilot/reviews/**` and `.pilot/state.json`**; H03 blocks shell writes to them | Without this, Claude could write a fake "pass" review file and mark a step done. Only `pilot.js review`, which runs the acceptance tests itself, writes review files |
| 3 | **Edits to `.pilot/manifest.json` and `.claude/settings*.json`** ask the owner (main session) and are denied for subagents | Changing `checks.fast` to a command that always passes would silently disable the end-of-turn gate |
| 4 | The "test config that excludes tests" rule moved from H03 to H02 | Config files are edited with Edit/Write, not shell commands |
| 5 | `/pilot:step` records the acceptance run through `pilot.js review`, not by Claude typing an exit code | The exit code is now real evidence |
| 6 | C-budget is a local release check, not a CI job | `plugin details` needs login (PR-5) |
| 7 | **E-03, E-04a–c and E-08 run as probes**, not plugin-eval cases | `claude plugin eval` loads no project settings, so the output style and rules cannot be tested there |
| 8 | **E-10 dropped from the evals** | It would need a full `/pilot:step` run inside an eval. Benchmark task B-2, with its misleading bug report, measures the same failure, F17 |
| 9 | **Reference solutions added for every benchmark task**, with a CI-run test proving the hidden tests pass on them and fail on the starting project | P3 did not require this, but without it a wrong hidden test would silently penalize both arms |
| 10 | **The pilot arm loads a stripped copy of the plugin**, and the sandbox denies reading the benchmark task folder | Otherwise the agent could find hidden tests or reference solutions through the plugin path its skills mention |
| 11 | Benchmark "lint errors" metric = `tsc --strict` errors (TypeScript) and `compileall` errors (Python) | A separate linter would need network installs per run and adds no failure mode the hidden tests and the reviewer miss |
| 12 | Benchmark projects use `design: not-applicable` in the pilot arm | The vanilla arm has no design step. A design reminder would make the arms unequal |
| 13 | **No nested Claude sessions from inside your session** | One nested call failed with an OAuth refresh error. Running more could disturb your login, so live probes run in WSL2 with their own token |

## 5. Bugs the kit's own tests caught during the build

- **The golden-project test** found that the TEST-STRATEGY template used `FR-012` as an example, which the ID check flagged as a dangling reference. Fix: IDs inside code formatting are treated as examples.
- **The benchmark validation test** found three tooling problems:
  - Windows' shell split the commit message.
  - Python could not import from a folder whose name starts with a dot.
  - A nested `node --test` inherited the parent runner's context and printed nothing.

  All three are fixed. Without the validation test, the benchmark would have recorded every run as a failure.
- **Schema files** had unescaped backslashes in regex patterns. The schema tests caught it.

## 6. What the owner does next

### 6.1 Set up WSL2 (one time, about 30 minutes)

In PowerShell as administrator, then reboot:

```powershell
wsl --install -d Ubuntu-24.04
```

In Ubuntu, install the tools:

```bash
sudo apt-get update && sudo apt-get install -y git bubblewrap socat ripgrep python3 curl build-essential gh pipx
curl -fsSL https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash && . ~/.nvm/nvm.sh && nvm install 24
curl -fsSL https://claude.ai/install.sh | bash
```

Create the long-lived login token and store it where only you can read it:

```bash
mkdir -p ~/.config/pilot-bench && claude setup-token
```

Paste the printed token into `~/.config/pilot-bench/token`, then:

```bash
chmod 600 ~/.config/pilot-bench/token
```

Copy the repo into the Linux home folder, not `/mnt/c`, which is much slower:

```bash
git clone "/mnt/c/Users/ghadi/Desktop/Master pilot" ~/pilot
```

### 6.2 Run, in this order

```bash
cd ~/pilot && npm test                      # free; should print 57 pass
node scripts/pilot.js doctor --bench --project ~/pilot   # bench prerequisites
node bench/probes.mjs --only PR-1,PR-3,PR-4,PR-6         # small: 4 short sessions
node bench/probes.mjs --only E-03,E-04a,E-04b,E-04c,E-08 # about 50 short sessions
npm run eval -- --allow-tools Write Edit Bash            # 9 cases x 3 runs x 2 arms
node bench/run.mjs --calibrate                           # 2 benchmark runs; prints the projected cost
```

After the calibration, Claude reports the real time and usage, and you decide whether to run the remaining 28 runs (P3 answer 1):

```bash
node bench/run.mjs --all && node bench/report.mjs
```

### 6.3 Publish (after the benchmark, and only with your go-ahead)

1. Create the GitHub repo, then replace `OWNER` in README.md and `scripts/lib/scaffold.js` (`PILOT_ACTION_REF`).
2. Push, and let kit CI run on Windows, macOS and Linux.
3. Tag with `claude plugin tag --push`. Version 0.1.0 stays marked pre-release until the benchmark passes.

## 8. Known limits of v1

- **Review verdicts.** The orchestrating session writes the reviewer's verdict to a file before `pilot.js review` records it. The acceptance exit code is real evidence. The verdict is only as honest as the orchestrator's copy of the reviewer's output. The benchmark's blind reviewer measures whether this matters.
- **Injection scanning.** The scanner (H07) uses patterns. It flags obvious planted instructions, not clever ones. The real protection is that deny rules and H03 block the damaging actions whatever Claude decides.
- **Node is required.** The guards fail closed, so a machine without Node on PATH gets blocked edits in pilot projects, and in every project if the plugin is enabled globally, until Node is installed. The README says so.
- **`/pilot:migrate` is not built yet.** v1 records the version and file fingerprints it will need.
